# Sources and authority

Separate inspected fact, observed presentation, confirmed decision, proposal,
assumption and superseded material. Retain location/anchor, known version or digest,
applicable environment and read scope. Unknown identities stay unknown; conversation
input can be identified as the user's input in this invocation without a fake URL.
A copied Slack decision in a PRD remains the same decision, not corroboration twice.

Read the original relevant input before adopting a summary. For a Slack thread,
distinguish proposals, actual decisions, unanswered questions, promised follow-up
and replaced decisions. A partial thread may omit its final outcome. Resolve a
conflict through explicit authority, scope and supersession; otherwise preserve
both claims and a decision question. Current code does not override a requested
future contract, and a future contract is not proof of current deployment.

Maintain SPEC §2.3's small reverse-coverage table: important original claim → section/
AC, question or explicitly authorized exclusion. Include visual/decision constraints
not already in upstream ACs. Do not transpose every source sentence into another
inventory. Preserve original IDs and close anchors so another reader can check it.

For visuals, identify the actual image/frame, selected variant, role, state, viewport
and version where available. Inspect the image before describing its appearance.
Record what was observed separately from measurement estimates and behavior inferred
from appearance. A static button image supplies no save/cancel/retry/permission/API
contract. Relevant absent behavior becomes a question, not an assumed interaction.

For each applicable API action record method/path/operation, request timing and role,
request versus response direction, required/optional and null separately, enum
values, error status/shape, schema pointer/version/environment and FE mapping.
Examples are not complete schemas. Distinguish 202 acceptance from completed
persistence and confirmed requery. Planned, implemented and deployed are different
claims. Contract not deployed and contract undecided have different impacts.

Inspect only relevant app entrypoints, API clients/types, query owners, validation,
components/tokens and maintained error/state patterns. Reuse findings as constraints
or observed patterns with exact locations, not automatic product policy. Do not
turn writing a specification into an application refactor or whole-repository audit.
