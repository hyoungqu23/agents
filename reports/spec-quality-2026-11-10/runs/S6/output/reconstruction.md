# 프로젝트 상태 필터와 선택 패널 — 독립 독자 재구성

## 1. 검토 범위와 증거 구분

이 문서는 인계받은 FE 개발자의 inspect-only 재구성이다. 기존 SPEC/QUESTIONS, 원자료, 스킬, 코드는 수정하지 않았다. 질문은 QUESTIONS에 등록하지 않았으며, 아래의 미확인 사항만 이 산출물에 기록한다.

실제로 읽은 파일은 다음과 같다.

- 현재 실행 지시: `/private/tmp/skill-quality-20261110/spec/runs/S6-reader/prompt.txt` 전체.
- 적용 스킬: `/private/tmp/skill-quality-20261110/spec/candidate/SKILL.md`, `references/sources-and-authority.md`, `references/readiness-and-updates.md` 전체.
- 인계 정본: `/private/tmp/skill-quality-20261110/spec/runs/S1-ready/output/SPEC.md` 전체. frontmatter의 identity는 `spec:project-status-selection`, revision 2, handoff_version 1, status ready이다.
- 동반 질문: `/private/tmp/skill-quality-20261110/spec/runs/S1-ready/output/QUESTIONS.md` 전체. identity는 `questions:project-status-selection`, revision 1, handoff_version 1이다.
- 위 문서가 이름으로 참조한 `/private/tmp/skill-quality-20261110/spec/runs/S1-ready/sources/`의 `request.md`, `api.md`, `DESIGN.md`, `ux.md` 전체와 `selected-reference.png` 전체 이미지. 텍스트 원자료의 내용과 이미지를 직접 대조했다. 별도 digest 계산은 하지 않았다.

다른 실행 기록, helper 결과(`spec-check.json` 포함), 다른 사례, 채점 자료, 부모 워크트리, 앱 코드, 실서버는 열지 않았다. Git·브라우저·외부 게시·위임·앱 실행·테스트를 수행하지 않았다.

아래에서 **본문으로 확정**은 SPEC 본문을 읽은 개발자가 원자료를 다시 열지 않아도 도출할 수 있는 계약을 뜻한다. **원자료 대조**는 이번 독자가 그 계약을 지정 원자료와 비교했다는 뜻이며, 앱의 실행 증거를 뜻하지 않는다. **미확인**은 원자료까지 읽어도 정해지지 않은 사항이다. 새 정책을 추가 가정으로 채택하지 않았다.

## 2. AC별 재구성

### AC-1 — 상태 선택과 실제 목록·개수

| 항목 | 본문으로 확정되는 구현 계약 |
| --- | --- |
| Actor | 프로젝트 목록을 사용하는 사용자. 별도 역할·쓰기 권한 정책은 이번 범위에 없다. |
| 초기 상태 | 목록 화면에 보이는 `Status` 레이블과 선택 입력이 있다. 현재 필터는 정해져 있다. 최초 필터가 무엇인지는 전제하지 않는다. 검증에서는 요청의 응답을 제어할 수 있다. |
| 행동 | 사용자가 All / Active / Archived / Paused 중 다른 Status로 변경한다. |
| 요청 | 변경 시 `GET /api/projects`를 보낸다. query는 All→`status=all`, Active→`status=active`, Archived→`status=archived`, Paused→`status=paused`이다. body는 없다. 선택 값 생략·null·다른 enum을 생성하지 않는다. |
| 진행 상태 | loading을 성공 empty 및 요청 error와 구별한다. 선택된 프로젝트가 있으면 패널을 유지한다. 이전 목록을 남기는 세부 방식은 기존 앱 관례를 따를 수 있으나, 이전 목록·개수를 새 필터의 성공 결과로 오인하게 표시할 수 없다. |
| 성공 결과 | 최신 요청의 200 `Project[]` 배열을 목록에 표시한다. 행에는 실제 `name`과 `status`를 표시하고, 개수는 배열의 `length`이다. 응답 상태 active / archived / paused를 Active / Archived / Paused로 표현한다. All은 요청용 값이다. 이미지의 데이터와 개수 3을 고정하지 않는다. |
| 빈 성공 | 최신 200 응답이 `[]`이면 결과 없음과 개수 0이다. 오류나 실패 Retry 화면으로 바꾸지 않는다. |
| 실패 결과·회복 | 최신 503 `{error:string}`이면 성공 empty와 다른 오류 UI 및 Retry를 표시한다. 실패를 `[]`와 0으로 변환하지 않는다. 현재 필터·선택은 유지하며, 이후 Status 변경 또는 AC-3의 Retry로 회복한다. 다른 요청의 늦은 완료는 AC-3의 최신성 규칙을 따른다. |
| 추가로 추측해야 하는 사항 | AC의 사용자 변경 이후 경로에는 새 행동 가정이 필요하지 않다. 최초 기본값·첫 조회 시점은 Q-002, 실제 endpoint 배포는 Q-001이다. 오류·로딩의 정확한 문구/컴포넌트는 기존 앱을 확인해야 한다. 이를 이 문서에서 결정하지 않는다. |
| 본문 위치 | SPEC §3.2 Status 조회, §4 Status/결과 목록, §5.1~5.3, §6.1 AC-1. |

검증 가능한 예: 네 필터에 각각 서로 다른 배열을 응답시켜 query, 표시 이름·상태, 개수를 대조한다. 0 / 1 / 여러 항목의 응답을 사용한다. 단순히 선택 입력의 표시만 바꾸거나 전체 데이터를 클라이언트에서 필터링하는 구현은 이 계약을 충족하지 않는다.

### AC-2 — 선택 객체 유지와 재등장 표시

| 항목 | 본문으로 확정되는 구현 계약 |
| --- | --- |
| Actor | 현재 성공 목록에서 프로젝트를 선택하는 사용자. |
| 초기 상태 | 현재 성공 목록에 프로젝트 P가 있다. P는 `id:string`, `name:string`, `status:active/archived/paused`의 필수 non-null 필드를 가진다. 최초 자동선택을 전제하지 않는다. |
| 행동 | 사용자가 P를 선택한다. 이후 P가 없는 필터, 빈 성공 필터를 조회하고, P가 있는 결과로 돌아온다. 다른 프로젝트를 선택할 수도 있다. |
| 요청 | 행 선택 자체는 추가 API를 부르지 않는 FE 상태 변경이다. 필터 변경은 AC-1의 GET을 사용한다. 선택 복구에도 별도 API나 쓰기 요청이 없다. |
| 선택 직후 성공 결과 | 현재 목록과 별도로 보유하는 선택 객체가 P로 바뀐다. 패널에 P.name을 표시하며 현재 목록의 P.id 행에 선택 표시를 한다. 다른 프로젝트를 선택하면 선택 객체가 교체된다. |
| 목록에서 사라진 결과 | 필터 응답에 P가 없어도 선택 객체와 패널 이름을 지우지 않는다. 필터 배열 교체는 선택 초기화의 이유가 아니다. |
| 빈 성공 | 최신 200 `[]`이면 목록은 결과 없음, 개수 0이고 기존 패널은 유지된다. 오류 상태가 아니다. |
| 복귀 결과 | 후속 목록에 같은 id가 다시 나타나면 해당 행에 선택 표시를 복구한다. 배열 위치·이름으로 대응하지 않는다. |
| 실패 결과·회복 | 선택 자체에는 명시된 서버 실패가 없다. 후속 필터 조회가 loading/error/Retry 상태여도 P의 선택과 패널을 유지한다. 실패 표현·Retry는 AC-3을 따른다. |
| 유지 경계 | 이 화면에서 필터 변경·loading·empty·error·Retry가 일어나는 동안 유지한다. 새로고침·라우트 이탈 후 보존이나 저장소 영속화를 요구하지 않는다. |
| 추가로 추측해야 하는 사항 | 명시된 P 선택→숨김→빈 성공→동일 id 복귀에는 새 행동 가정이 필요하지 않다. 초기 미선택 표현은 Q-002이다. 같은 id가 변경된 name으로 재등장할 때 패널 이름을 새 응답에 맞춰 갱신하는지는 정해지지 않았다(§4 참조). |
| 본문 위치 | SPEC §2.2, §3.2 행 선택/필터 밖 선택/성공 empty, §4 선택 패널, §5.1 선택/§5.2 id/name, §6.1 AC-2. |

검증 가능한 예: P를 선택한 뒤 목록 순서·개수를 바꾸고 P를 제거한다. 패널 이름이 유지되는지 확인한 다음 빈 성공을 보낸다. P와 같은 id를 다른 위치에 다시 넣었을 때 해당 행의 선택 표시가 돌아오는지 확인한다. 이 기본 시나리오에서 P의 이름이 바뀐다는 가정은 넣지 않는다.

### AC-3 — 실패·현재 필터 Retry·요청 최신성

| 항목 | 본문으로 확정되는 구현 계약 |
| --- | --- |
| Actor | 필터를 변경하거나 오류 화면에서 Retry를 실행하는 목록 사용자. |
| 초기 상태 | 프로젝트 P를 선택한 상태이며 현재 필터 요청이 진행 중이다. 검증에서는 요청 시작·성공·실패·finally의 완료 순서를 제어할 수 있다. |
| 행동 | 최신 요청을 실패시키고 Retry를 실행한다. 또는 요청 A 이후 필터 변경이나 동일 필터 Retry로 새 요청 B를 시작하고 A/B를 역순으로 완료시킨다. |
| 요청 | Retry 클릭 시점의 현재 Status로 `GET /api/projects?status=…`를 다시 보낸다. 이전 실패 요청이 캡처한 필터 값으로 대체하지 않는다. Retry도 새로운 최신 요청이다. |
| 최신 실패 결과 | 확정 실패 계약인 503 `{error:string}`을 성공 empty와 구별한 오류 및 Retry로 표시한다. 현재 Status와 P의 선택 객체·패널 이름을 유지한다. error 문자열을 그대로 출력해야 한다는 계약은 없다. |
| Retry 진행·성공 | 새 요청은 loading으로 진행하며 P를 유지한다. 그 요청이 여전히 최신이고 200이면 실제 배열·개수, `[]`이면 결과 없음·0으로 회복한다. |
| Retry 재실패 | 여전히 최신인 요청이 다시 실패하면 오류/Retry 상태를 유지하며 P를 비우지 않는다. |
| 오래된 결과 | B가 시작된 뒤 A의 성공·실패·finally는 현재 목록·개수·오류·loading 종료를 바꿀 수 없다. B 대기 중 A finally가 도착해도 B의 loading을 끝내지 않는다. B 완료 후 A가 도착해도 B의 결과를 덮지 않는다. 동일 필터의 이전 요청에도 적용한다. |
| 구현 재량 | 세대 식별·취소·상태 관리 방식은 개발자 재량이다. 취소를 사용하더라도 오래된 finally까지 무시하는 외부 결과를 보장해야 한다. |
| 추가로 추측해야 하는 사항 | 명시된 503/Retry/완료 순서 경로에는 새 행동 가정이 필요하지 않다. 네트워크 실패·다른 HTTP status의 구체 응답 schema는 없고 기존 실패/Retry 경로를 사용하되 성공 empty로 합치지 않는 원칙만 정해져 있다. 실제 오류 컴포넌트는 제공되지 않았다. |
| 본문 위치 | SPEC §3.2 실패·Retry/응답 역전, §4 loading/error/Retry, §5.1 Retry 및 §5.3, §6.1 AC-3. |

검증 가능한 예: 200+[]와 503을 각각 보내 성공 empty와 오류가 구별되는지 확인한다. B를 대기시킨 채 A의 성공·실패·finally를 각각 늦게 전달한다. B 성공 뒤 A 실패, B 실패 뒤 A 성공도 확인한다. 목록·개수·오류뿐 아니라 loading이 오래된 finally로 종료되지 않는지 관찰한다. 모든 경우 P의 패널을 함께 확인한다.

## 3. 세 AC에 공통으로 재구성되는 제약

- 읽기 전용이다. 저장·보관을 포함한 쓰기 API와 새 권한 정책을 추가하지 않는다. 보관된 상태의 프로젝트를 조회하는 Archived 필터는 포함한다.
- 목록 위에 보이는 Status 레이블과 네 선택 값을 제공하며 입력에 키보드 focus가 있어야 한다.
- `--accent:#2457c5`, 흰 `--surface`, `--line:#d8dee9`, `--space:24px`를 사용한다. 이미지의 주황 선택 테두리를 시스템 색으로 채택하지 않는다.
- 넓은 화면에서는 목록/선택 패널 2열, 너비 700px 이하에서는 패널이 목록 아래이다. 700px와 701px 경계를 확인할 수 있다.
- 이미지의 제목·설명, 목록 위 필터/개수, 이름·상태 행, 별도 선택 패널 구조는 SPEC §3.1에 서술되어 있다. 정확한 열 비율·폰트·모서리·픽셀 여백은 확정하지 않았다. 내부 컴포넌트·라이브러리 선택도 개발자 재량이다.

## 4. 본문·원자료·미확인 사항의 경계

| 분류 | 이번 독자가 확인한 내용 | 개발자가 추가로 해야 하는 일 |
| --- | --- | --- |
| 본문으로 재구성됨 | 세 AC의 actor, 사용자 선택 이후 사전 상태, GET/query 매핑, 200 배열/length, 503/error/Retry, 독립 선택 객체, id 복귀, 빈 성공 구별, 오래된 성공·실패·finally 무시, 토큰·700px·label/focus, 읽기 전용 경계가 모두 본문에 있다. | 명시된 계약을 구현하고 실제 동작으로 검증한다. 핵심 AC를 이해하기 위해 원자료에서만 새로 찾아야 하는 규칙은 발견하지 못했다. |
| 원자료를 직접 읽어야 확인할 수 있는 사실 | SPEC의 출처 요약이 원문과 맞는지, Target contract v1이 문서상 확정인지, 주황이 데모 값인지, finally가 원 UX 규칙에 포함되는지는 인계 문서의 자기 주장만으로 독립 확인할 수 없다. 이번에는 지정 원문을 읽어 해당 내용을 대조했다. 이미지도 직접 열어 All·3 projects·Tide 선택의 정적 화면과 주황 테두리, 2열 구조를 확인했다. | 문서의 권위·정확성을 인증하려면 원문 대조가 필요하다. 이번 대조에서는 위 핵심 규칙의 누락·충돌을 발견하지 못했다. 독자 동의는 실행 또는 독립적 진실의 증명이 아니다. |
| 원자료까지 읽어도 미확인: Q-001 | 실제 연결 환경에 Target contract v1이 배포되어 있는지, 실행 환경·배포 버전은 없다. QUESTIONS에서 open/no이다. | 실서버 통합 전에 환경·배포 또는 실제 요청/응답 증거를 확인한다. 제어 응답을 쓰는 FE 구현·AC 검증과 구별한다. |
| 원자료까지 읽어도 미확인: Q-002 | 최초 Status 기본값, 첫 조회 시점, 자동선택 여부, 미선택 패널 문구는 없다. QUESTIONS에서 open/no이다. All·Tide가 보이는 정적 이미지는 초기 진입 정책을 증명하지 않는다. | 기존 진입 코드·관례 또는 확정 요구를 확인한다. 이 재구성은 임의의 All 기본값이나 첫 행 자동선택을 채택하지 않는다. 사용자 선택 이후의 세 AC는 독립적으로 구현할 수 있다. |
| 기존 앱 확인 필요 | 기존 오류/Retry·loading의 구체 컴포넌트와 문구, 실제 토큰 정의 위치·API client·초기화 경로는 제공되지 않았다. SPEC은 재사용 방향과 외부 결과만 정한다. | 통합 시 대상 코드에서 해당 위치·관례를 확인한다. 여기서 구현 파일명이나 컴포넌트 이름을 추측하지 않는다. |
| 추가로 발견한 해석 경계: AC-2 | 같은 id의 name이 후속 응답에서 달라질 때, 별도 선택 객체의 패널 이름을 새 값에 동기화하는지 선택 당시 값을 유지하는지는 SPEC과 원자료 모두 명시하지 않는다. 필터 사이에서 선택 유지·id 표시 복구가 필요하다는 점만 확정된다. 기존 QUESTIONS에는 이 항목이 없다. | 해당 데이터 변경까지 지원·검증해야 한다면 이름 갱신 정책을 확인한다. 이 산출물은 어느 쪽도 확정하지 않았고 QUESTIONS를 수정하지 않았다. 기존의 동일 이름 P 시나리오는 이 결정 없이 재구성된다. |
| 추가 정책을 도출하지 않음 | 빈 문자열 허용, 계약 밖 enum/null 응답의 세부 처리, 재진입 영속화, 동일 Status 재선택 시 추가 요청 여부는 주어진 핵심 전이로 확정하지 않았다. | 필요가 생기면 계약/기존 동작을 확인한다. 정상 계약 검증에 임의 fallback·쓰기·새 영속화 정책을 섞지 않는다. |

## 5. 재구성 결과와 한계

정본 §6.1의 AC-1, AC-2, AC-3 세 행을 모두 위에서 재구성했다. 명시적인 사용자 선택 이후의 조회·선택 유지·빈 성공·오류·Retry·응답 역전 동작은 SPEC 본문에 충분히 드러나며, 원자료 대조에서도 이 경로에 대한 상충을 발견하지 못했다. 문서의 ready 표시는 이 결과와 별개로 문서 준비 상태이고 구현·배포 완료 증거가 아니다.

초기 진입과 실환경 통합에는 열린 Q-001/Q-002의 확인이 필요하다. 변경된 프로젝트 이름의 동기화는 추가로 발견한 미정 경계이다. 원자료가 정의하지 않은 동작을 사실로 보충하지 않았다. 이 검토는 별도 독자의 문서 재구성과 지정 출처 대조까지이며 코드 수정, 구조 helper 재실행, 런타임 API/앱 검증은 포함하지 않는다. 질문은 등록하지 않았다.
