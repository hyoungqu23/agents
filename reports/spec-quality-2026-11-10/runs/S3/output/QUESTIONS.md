# 거래처 초대 화면 — 미결 사항·해결 이력

- 대상 명세: [SPEC.md](./SPEC.md)
- 확인 범위: SPEC §2.1의 SRC-001~SRC-004 전체를 직접 읽었다. 이전 질문 원문 OD-permission은 Q-001에 연결해 보존했다. 참조 이미지와 schema는 미제공이며 후속 회의 결정도 확인하지 못했다.
- 자료 변경 후 확인할 것: 역할·API·화면·정책 자료가 도착하면 관련 SPEC 절과 AC-invite를 함께 재검토한다. 사용자 답변은 요청하지 않았으며 무응답을 결정으로 취급하지 않았다.
- 아래 표가 질문 상태와 차단성의 정본이다. 상세는 근거·영향·해결 조건을 기록한다.

## 2. 질문 상세

### Q-001 — OD-permission: 허용 역할과 권한 오류

- 원문 식별자: OD-permission(SRC-004). 새 ID로 대체하거나 기존 미결을 종결하지 않고 Q-001과 연결한다.
- 질문: 초대 가능한 역할과 화면/제출의 권한 표현, API 권한 오류 계약은 무엇인가?
- 근거·충돌: SRC-004 전체는 역할 및 API 권한 오류 계약 미정을 기록하고 담당자 확인을 deferred로 보류하며 구현 차단이라고 명시한다. SRC-002도 후속 회의 결정을 기다리며 답변이 없다고 한다. 상충하는 확정 답변은 없다.
- 현재 확인한 사실: AC-invite는 허용된 역할의 초대를 요구한다. 구체 역할과 오류 status/body/code는 확인하지 못했다.
- 구현 영향: 화면 접근, 제출 허용, 권한 없는 사용자의 표시와 오류/회복 동작을 결정할 수 없다. 일반 API schema는 Q-002, 결과 표현은 Q-008과 함께 맞춰야 한다.
- 차단성 이유: 기존 원문이 명시적으로 구현을 막는 질문이며 허용된 actor를 정의할 수 없다. 담당자 확인 보류는 해결 근거가 아니다.
- 해결에 필요한 것: 권한 있는 결정권자의 역할별 허용/거절 규칙과 서버 권한 오류 계약 및 FE 대응. 실제 확인 근거·판본도 필요하다.
- 결정권자·답변자: unknown. 담당자가 확인되었다고 주장하지 않는다.
- 필요한 시점·재확인 조건: 권한 흐름 구현/검증 전에 필요하다.
- 해결 결과: 답변과 결정 근거 없음. 기존 보류를 그대로 보존한다.
- SPEC 반영 위치: 미결로 §2.2, §3, §4, §5.1/§5.3, §6.1에 반영. 해결된 규칙은 아직 없다.

### Q-002 — 최종 API 계약과 대상 판본

- 원문 식별자: SRC-003 전체, AC-invite. 기존 Q/OD ID 없음.
- 질문: 최종 method/path/operation, 호출 시점·인증 전제, 요청 필드와 성공/일반 실패 응답, 적용 판본·환경·구현/배포 상태는 무엇인가?
- 근거·충돌: SRC-003에는 POST /invitations라는 이름만 공유되었고 최종 method·요청·성공·오류·배포 판본을 확인할 missing-contract.md가 첨부되지 않았다고 적혀 있다. 예제나 완결된 schema는 없다.
- 현재 확인한 사실: 공유된 API 표기만 있다. 입력/응답 필드명, 타입, required/optional, null, enum, status와 error shape는 미확인이다. 권한 오류는 Q-001의 기존 질문과 연결한다.
- 구현 영향: API client 호출·payload 생성·응답 파싱·완료 판정·오류 분기·재조회 필요 여부를 구현할 수 없다.
- 차단성 이유: 요청을 보내고 결과를 확인하는 AC-invite의 서버 경계가 결정되지 않았다. 계약 미정/미열람과 미배포를 구별해야 하며 현재는 어느 배포 상태도 단정할 수 없다.
- 해결에 필요한 것: 누락된 schema 원문 또는 동등한 승인 계약과 판본·적용 환경·상태. 접수와 초대 생성/발송 완료의 의미도 명시되어야 한다.
- 결정권자·답변자: unknown.
- 해결 결과: 원자료에 계약 없음. POST를 최종 확정으로 승격하지 않는다.
- SPEC 반영 위치: 미결로 §3.2, §4, §5 전체, §6.1에 반영.

### Q-003 — 재전송 범위와 조건

- 원문 식별자: SRC-002의 초대 재전송 후속 결정 기록, AC-invite.
- 질문: 이번 화면에서 재전송을 제공하는가? 제공한다면 대상, 권한, 허용 시점·제한, 사용자 행동·API·결과는 무엇인가?
- 근거·충돌: SRC-002는 후속 회의에서 정하기로 했고 결정 답변은 발췌에 없다고 명시한다.
- 현재 확인한 사실: 재전송 정책이 아직 정해지지 않은 관련 항목이다. 기존 초대를 새로 생성하는 방식인지 별도 요청인지 확인되지 않았다.
- 구현 영향: 재전송 UI 존재 여부, 제출 분기, 요청 계약과 결과/오류 처리, AC-invite에 해당되는 조건이 달라진다.
- 차단성 이유: 관련 정책을 임의로 제외하면 선언한 거래처 초대 화면 범위를 축소할 수 있다. 포함/제외의 권한 있는 결정부터 필요하다.
- 해결에 필요한 것: 적용 범위와 상세 정책의 승인 결정. 포함이면 API 계약 및 관찰 가능한 기대 결과가 함께 필요하다.
- 결정권자·답변자: unknown.
- 해결 결과: 결정 답변 없음. 제외로 간주하지 않는다.
- SPEC 반영 위치: §1, §3.2, §4, §5.1, §6.1.

### Q-004 — 만료 정책

- 원문 식별자: SRC-002의 만료 후속 결정 기록, AC-invite.
- 질문: 무엇이 언제 만료되는가? 유효기간과 경계, 만료 상태 표시 및 이후 초대/재전송 허용·회복 규칙은 무엇인가?
- 근거·충돌: SRC-002에 후속 결정 예정이라는 사실만 있고 결과는 없다.
- 현재 확인한 사실: 만료 정책이 미정이다. 기간·상태 enum·판정 주체·별도 만료 API가 있다고 확인하지 않았다.
- 구현 영향: 기존 초대가 만료된 대상의 요청 가능 여부, 결과 표시, 재전송과의 관계가 달라진다.
- 차단성 이유: 만료 조건에서 AC-invite의 허용 행동과 기대 결과를 정의할 수 없다. 임의 유효기간은 정책 발명이 된다.
- 해결에 필요한 것: 이 화면에 적용되는 만료 정책의 확정 원문과 서버 상태/응답 매핑. 적용되지 않으면 명시적 제외 결정이 필요하다.
- 결정권자·답변자: unknown.
- 해결 결과: 결정 답변 없음.
- SPEC 반영 위치: §1, §3.2, §4, §6.1 및 향후 확정 시 §5의 상태 매핑.

### Q-005 — 중복과 재요청 처리

- 원문 식별자: SRC-002의 중복 처리 후속 결정 기록, AC-invite.
- 질문: 중복의 기준은 무엇이며 동일 대상/기존 초대/기존 거래처 및 반복 제출에 대해 어떤 요청과 결과를 허용하는가?
- 근거·충돌: SRC-002는 중복 처리를 후속 회의로 넘겼다. 현재 자료에는 중복 판별 키나 최종 응답이 없다.
- 현재 확인한 사실: 중복 정책 미정. 중복을 무조건 오류로 간주하거나 재전송으로 자동 전환할 근거가 없다.
- 구현 영향: 제출 활성, 요청 횟수와 중복 방지, 서버 응답 분기, 안내·회복 경로가 달라진다.
- 차단성 이유: 반복되거나 기존 대상인 초대 요청의 관찰 결과를 확정할 수 없어 AC-invite의 실질 조건이 빠져 있다.
- 해결에 필요한 것: 중복 정의와 허용/거절/기존 결과 반환 규칙, 요청 중 재제출 정책, 계약과 UI 매핑.
- 결정권자·답변자: unknown.
- 해결 결과: 결정 답변 없음.
- SPEC 반영 위치: §1, §3.2, §4, §5.3, §6.1.

### Q-006 — 누락된 화면 자료와 표현 계약

- 원문 식별자: SRC-002가 언급한 invitation-frame.png(SRC-005), AC-invite.
- 질문: 검토할 실제 화면 판본·선택 variant·역할/상태·viewport, 진입/이탈 경로와 적용할 UI 표현 제약은 무엇인가?
- 근거·충돌: SRC-002는 화면 파일이 아직 오지 않았다고 명시한다. 제공 sources 목록에는 PNG가 없다.
- 현재 확인한 사실: 이메일 입력이라는 텍스트 요구만 있다. 레이아웃·폼 구조·버튼·문구·모달/페이지 형태는 관찰하지 못했다. 디자인 시스템·접근성·반응형 자료도 제공되지 않았다.
- 구현 영향: 화면 구조와 표시 위치를 정할 수 없다. 이미지가 도착해도 정적 표현과 인터랙션 계약을 구분해 읽어야 한다.
- 차단성 이유: 사용자가 관찰할 화면의 구현 근거가 없으며 임의 화면을 최종 계약으로 만들 권한이 없다.
- 해결에 필요한 것: 실제 선택 화면 또는 승인된 텍스트 UI 계약, 대상 환경과 적용 제약. 이미지로 확인되지 않는 동작은 Q-008 등에서 별도 결정한다.
- 결정권자·답변자: unknown.
- 해결 결과: 파일 미제공. 보지 않은 이미지의 구조나 동작을 서술하지 않는다.
- SPEC 반영 위치: §1, §2.1, §3.1, §4, §6.1.

### Q-007 — 이메일 입력 규칙

- 원문 식별자: SRC-002의 이메일 입력 기록, AC-invite.
- 질문: 입력 개수·필수 여부·형식/길이·공백/대소문자 변환, 검증 시점·오류 표시와 제출 허용 조건은 무엇인가?
- 근거·충돌: SRC-002는 이메일 입력 필요만 기록하며 상세 검증 규칙은 없다. API 요청 필드는 SRC-006 누락으로 미확인이다.
- 현재 확인한 사실: 초대 대상 이메일을 입력한다. 단일 입력, 특정 정규식, trim/lowercase 또는 필수 필드라고 확정할 근거는 없다.
- 구현 영향: 입력 UI·검증·값 변환·payload와 오류 처리 조건이 달라진다.
- 차단성 이유: 어떤 입력에서 요청해야 하는지와 실패가 무엇인지 정할 수 없다.
- 해결에 필요한 것: 입력 규칙과 UI 검증/서버 검증 경계 및 오류 표현, Q-002의 필드 매핑과 일치하는 결정.
- 결정권자·답변자: unknown.
- 해결 결과: 결정 근거 없음.
- SPEC 반영 위치: §3.2, §4, §5.2, §6.1.

### Q-008 — 제출·결과 확인과 회복

- 원문 식별자: SRC-001 AC-invite의 요청 전송·결과 확인 목표.
- 질문: 어떤 행동이 언제 요청을 발생시키며, 접수/초대 생성/발송 중 무엇을 완료로 표시하는가? 성공/실패 UI와 입력 유지·초기화·재시도·이탈은 어떻게 동작하는가?
- 근거·충돌: SRC-001의 결과 확인은 목표이고 SRC-002에는 이를 구체화한 동작이 없다. SRC-003도 성공/오류 계약을 제공하지 않는다.
- 현재 확인한 사실: 허용된 역할이 요청하고 결과를 확인해야 한다. 토스트·인라인 문구·목록 갱신·화면 닫힘·재조회 중 어떤 방식도 확인되지 않았다.
- 구현 영향: 요청 트리거와 진행/결과 상태, 성공 후 변화, 실패 시 다음 행동 및 보존할 데이터가 달라진다.
- 차단성 이유: AC-invite의 Then을 관찰 가능한 결과로 재구성할 수 없다. schema가 있어도 FE 표시·회복 정책이 자동으로 결정되지는 않는다.
- 해결에 필요한 것: Q-001/Q-002의 응답 계약을 바탕으로 한 사용자 행동→조건→UI 결과→다음 행동의 승인 규칙과 Q-006의 표현 연결.
- 결정권자·답변자: unknown.
- 해결 결과: 결정 근거 없음.
- SPEC 반영 위치: §3.2, §4, §5.1~§5.3, §6.1.

## 3. 해결·보류·재개 이력
