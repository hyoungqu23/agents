# 프로젝트 필터 FE 명세 읽기 전용 검토

## 판정

**현재 SPEC의 `ready`를 지지할 수 없다. 개발 기준으로 준비되지 않았다.** 형식상 인계 문서는 유효하지만, 핵심 구현 규칙이 본문과 AC 사이에서 서로 반대다. 제공된 확정 결정으로 바로잡을 수 있는 두 오류와, 자료만으로 결정할 수 없는 계약 누락을 구분했다. 전체 범위를 인계하려면 아래 수정과 계약 확인이 필요하다. 누락 계약을 미해결 차단 질문으로 등록하는 경우 권고 상태는 `blocked`다. 기존 파일의 상태·리비전·내용은 변경하지 않았다.

## 읽은 자료와 권위

다음 원문을 모두 읽었다. 파일 날짜나 기존 `ready` 표시는 권위 근거로 사용하지 않았다.

| 자료 | 확인한 식별·범위 | 이 검토에서의 역할 |
| --- | --- | --- |
| `sources/SPEC.md` | `spec:filter-review`, revision 4, handoff v1, 1–31행 전체 | 검토 대상. 기존 작성자의 검토 통과 기록은 과거의 주장으로 취급 |
| `sources/QUESTIONS.md` | `questions:filter-review`, revision 4, handoff v1, 1–11행 전체 | 검토 대상. 정식 질문 표에는 행이 없음 |
| `sources/api.md` | Target v2, 1행 전체 | 주어진 목표 API 계약. 실제 배포 여부·환경·Project 스키마 위치는 제공되지 않음 |
| `sources/decisions.md` | 확정 `DEC-filter`, 1행 전체 | 필터 요청 및 Retry 정책의 명시적 결정 |

적용한 스킬과 그 두 참조 문서, 구조 검사기 및 파서도 읽었다. 다른 사례·저장소·외부 자료·실행 앱은 읽거나 검사하지 않았다. Target v2는 목표 계약을 뜻하며 운영 서버의 구현·배포 증거가 아니다.

## 발견 사항

### F-01 · 필터 변경 시 서버 요청을 생략하는 본문은 확정 결정과 반대다

- 위치: `SPEC.md:14`(§3), `SPEC.md:18`(§5의 요청 정책 위임), `SPEC.md:23`(`AC-fetch`).
- 원문: `api.md:1`은 각 status 결과를 서버가 필터링한다고 규정한다. `decisions.md:1`은 필터를 바꿀 때마다 해당 status로 요청하고 클라이언트만의 필터링은 채택하지 않았다고 명시한다.
- 충돌: §3을 따르면 최초 All 결과를 로컬에서만 거른다. `AC-fetch`를 따르면 선택한 status로 실제 GET 요청을 보낸다. §5는 잘못된 §3을 다시 요청 정책으로 지목한다.
- 영향: `AC-fetch`. 최초 All 응답만으로 다른 상태의 결과를 얻을 수 있다는 보장도 없다. 본문을 따르는 구현은 AC의 요청 관찰 검증에 실패한다.
- 필요한 조치: §3과 §5에 필터 변경 → 선택 status를 담은 GET → 해당 응답 표시를 일관되게 명시하고 로컬 전용 필터 규칙을 제거한다. `AC-fetch`의 ID와 올바른 기대는 유지한다. 이미 확정된 정책이므로 사용자에게 두 대안 중 선택을 다시 요청할 사안이 아니다.

### F-02 · Retry의 All 초기화·선택 해제는 확정 결정 및 문서 자체와 반대다

- 위치: `SPEC.md:10`(§1), `SPEC.md:16`(§4), `SPEC.md:18`(§5), `SPEC.md:24`(`AC-retry`).
- 원문: `decisions.md:1`은 Retry 시 현재 필터와 기존 프로젝트 선택을 유지하며, All 초기화와 선택 해제를 채택하지 않았다고 명시한다.
- 충돌: §4는 필터를 All로 바꾸고 선택을 해제한 뒤 All을 다시 요청한다. §1과 `AC-retry`는 기존 상태 유지를 요구한다. §5의 위임 때문에 API 요청값도 반대로 갈린다.
- 영향: `AC-retry`. 오류 전 `active`와 프로젝트 선택이 있던 사용자는 본문 구현에서 상태를 잃고 `status=all` 요청을 보내게 된다.
- 필요한 조치: Retry → 현재 status로 재요청 → 필터·선택 유지 → 성공 결과로 회복하도록 §4·§5를 맞춘다. `AC-retry`와 선택 유지 규칙은 보존한다. 이 역시 새 의사결정이 필요한 충돌이 아니다.

### F-03 · API 표현과 FE 상태 매핑이 전체 구현을 재구성하기에 부족하다

- 위치: `SPEC.md:18`, `api.md:1`, `AC-fetch`, `AC-retry`.
- 확인된 계약: `GET /api/projects`, query status는 `all`, `active`, `archived`, `paused`; 성공은 `200 Project[]`; `503` 본문은 `{error:string}`. SPEC은 성공 상태 코드와 503 본문 구조를 생략했다. 이는 원자료에서 그대로 보완할 수 있다.
- 실제 미제공 자료: `Project` 필드·식별자·필수/선택·null 허용 여부와 스키마 위치. AC는 결과 ID 대조와 프로젝트 선택 유지를 요구하지만 식별자 계약은 제공되지 않았다.
- 실제 미결 매핑: 503의 error와 표시 문구 관계, 재시도 중 및 재실패 후 목록·선택 패널의 표시 상태, 필터를 빠르게 바꿨을 때 늦은 이전 응답을 반영하는 규칙은 정해져 있지 않다. 이 동작을 임의로 확정해서는 안 된다.
- 영향: 두 AC의 응답 매핑과 오류 회복 구현. API 계약에서 모르는 항목을 ‘해당 없음’이나 배포 완료로 간주할 수 없다.

### F-04 · 검토 통과·미결 없음 기록은 실질 준비 완료를 입증하지 못한다

- 위치: `SPEC.md:12`, `SPEC.md:25`–`31`, `QUESTIONS.md:8`–`11`.
- §2는 작성자가 자료를 읽었다는 요약만 있고, 확정 규칙의 내용과 주요 원문 주장 → 본문/AC의 역추적 표가 없다. 예를 들어 서버 필터 정책은 AC에는 반영되지만 §3에서는 거부되는 상태다.
- §6.2에는 네 종류의 검토 행이 있으나 결과는 모두 ‘통과라고 기재됨’이다. 이번 원문 대조에서 발견한 F-01·F-02 때문에 그 기록을 현재 정합성의 증거로 재사용할 수 없다. 과거 작성자가 실제 무엇을 검사했는지는 확인하지 못했다.
- 질문 표가 비어 있다는 사실은 의문이 없다는 증거가 아니다. F-03의 미제공 계약과 동작을 해소하거나 영향이 없는 이유를 명시해야 한다.
- 조치 시에는 실제 수행한 검토의 범위·방식·한계를 기록하고, 확인된 정책은 SPEC 본문에 읽을 수 있게 남겨야 한다. 이번에는 읽기 전용이므로 해당 문서를 수정하지 않았다.

| --- | --- | --- |

| 원자료·권위·판본 대조 | API Target v2와 확정 DEC-filter 원문을 본문·AC와 대조 | F-01·F-02 발견. 스키마·운영 환경·배포 상태는 검증하지 못함 |

검토는 **동일한 검토자의 자기 검토**다. 별도 에이전트·두 번째 독립 독자는 사용하지 않았다. 형식 검사 통과를 의미 정확성 또는 실제 앱 동작의 통과로 보고하지 않는다.

## 독립적으로 진행 가능한 범위와 검사 한계

문서 보완은 추가 정책 결정 없이 진행할 수 있다. 서버 요청 필터링, 현재 필터로 Retry, 필터·선택 유지, 네 query enum, 200/503 및 알려진 오류 본문을 일치시키는 작업이 해당한다. 이로써 원래 범위를 축소하거나 두 AC를 삭제할 이유는 없다. 응답 필드 및 미결 상태 매핑까지 포함한 두 AC의 완전한 FE 구현 인계는 아직 준비되지 않았다. 이 보고서는 구현·게시·배포 권한을 부여하지 않는다.

제공된 네 원자료 중 읽지 않은 자료는 없다. 외부 링크·디자인·실행 코드·실제 API 호출 결과는 제공되거나 검사되지 않았다. 브라우저·Git·외부 게시·위임을 사용하지 않았으며, 원래 SPEC/QUESTIONS와 원자료는 수정하지 않았다. 유일한 작성 산출물은 이 보고서다.
