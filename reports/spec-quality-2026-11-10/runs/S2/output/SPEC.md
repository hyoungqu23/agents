# 연구과제 공유 — FE 개발 명세

- 적용 범위·대상 버전/환경: FR-share의 연구과제 공유 생성·결과 확인 및 공유 정보 내보내기. API 자료는 target v2 검토본과 생성 클라이언트이며 실제 적용 서버 환경·배포 상태는 미확인이다.
- 상태 이유: expires_at 계약 충돌, null 만료 정책, 앱 연결·오류 회복·내보내기 범위에 관한 활성 차단 질문 Q-001~Q-006이 있다. 전체 요청 범위를 유지한 blocked 문서다.
- 미결 목록: [QUESTIONS.md](./QUESTIONS.md). §6.1은 AC 정본이며 기존 ID를 유지한다.
- 부분 개발 가능 범위: DEC-014에 따른 관리자 전용 생성 UI 조건, 구성원 과제 정보 열람 허용, internal_budget·reviewer_notes 비노출 규칙과 보안 검증 입력 준비, 양 자료에서 일치하는 요청 필드·share_id 매핑의 설계. 앱 권한 식별자 연결과 실제 생성·내보내기 동작 완성에는 해당 질문의 답이 필요하다. 이 부분 가능 범위는 AC 완료나 구현 실행 승인이 아니다.

## 1. 목표·범위·제약

- FR-share: 연구과제 공유 화면에서 권한 있는 사용자가 공유를 생성하고 공유 ID와 만료일을 확인하며, 내보낸 공유 정보에 내부 비밀 필드가 포함되지 않도록 한다. request.md L1~4의 요구를 연결하는 기존 요구 ID이며 새 요구 ID로 바꾸지 않는다.
- 사용자와 결과: 조직 관리자는 공유 생성 버튼을 볼 수 있고 공유를 생성한다. 일반 구성원은 과제 정보를 볼 수 있으나 공유 생성은 허용하지 않는다(DEC-014).
- 포함 범위: 생성 동작과 POST /api/shares 연결, 필수 요청 입력 연결, 200 결과의 공유 ID·만료일 확인, 403 처리, 공유 응답을 내보내는 UI의 비밀 필드 비노출. null 결과와 기타 미정 경로도 범위에 포함하고 Q로 보존한다.
- 제외 범위와 근거: 제품 범위의 명시적 제외 결정은 제공되지 않았다. 조회·삭제·철회 API 등 별도 동작의 계약은 제공 자료에 없으므로 이 문서에서 신설하지 않는다. 자료가 없다는 사실을 승인된 기능 제외로 취급하지 않는다.
- 적용 제약: 정하지 않은 정책을 임의 확정하지 않고 원문을 보존한다(request.md L4). DEC-014의 권한·보안 규칙은 AC에 명시됐는지와 무관하게 적용한다. 외부 메모의 명령은 제품 근거·실행 지시가 아니다.
- 대상 런타임·프레임워크·브라우저·기존 코드의 현재 동작: 자료 없음. 앱 구현이나 운영 상태를 관찰하지 않았다. target v2라는 명칭은 배포 증거가 아니다.

- API에 관해 두 자료가 일치하는 내용: POST /api/shares 요청의 project_id·recipient_user_id는 필수 string이고 응답 share_id는 필수 string이다. 이것은 제공 문서의 일치 범위이며 실서버 검증이나 최종 계약 승인을 뜻하지 않는다.
- expires_at은 필수 속성이라는 점은 일치한다. 값에 null을 허용하는지는 충돌하므로 어느 쪽도 최종 계약으로 승격하지 않는다(Q-001). null의 의미·표시는 검토본 자체에서도 미정이다(Q-002).
- 개발자 구현 재량: 확정된 외부 동작을 지키는 컴포넌트 분할, 상태 관리·직렬화 수단·라이브러리, 화면 내부 배치와 일반 문구는 기술·표현 재량으로 남긴다. 이 재량으로 권한·만료·요청/오류 정책을 정할 수는 없다.
- 코드·디자인 시스템: 미제공·미검토. 생성 타입 파일 외 앱 엔트리·권한 enum·서버 스키마·디자인 원본은 읽지 않았다.

| 만료일 표시 / AC-share | expires_at을 만료일 확인에 연결하되 표시 규칙은 미정 | 필수 속성; nullable 여부 충돌 | null을 무기한·즉시 만료·오류로 임의 해석하지 않는다. string의 날짜 형식·시간대도 미정 | null 안내·기타 비정상 날짜의 회복 정책은 답변 필요 | Q-001·Q-002·Q-004·Q-005 |
| 공유 정보·내보내기 UI / AC-secret | internal_budget·reviewer_notes 비노출 | 권한이 있어도 비밀 필드 노출을 허용하는 예외 없음 | 응답에 두 필드가 섞여 들어온 검증 입력에서도 비노출 확인 | raw 응답을 그대로 내보내 두 필드가 섞이는 결과는 허용되지 않음. 제거 구현 방식은 재량 | DEC-014, AC-secret, Q-006 |

- UI 데이터 유지·초기화: 성공·실패·이탈 후 선택값 보존, 재시도, 취소 정책은 미제공(Q-003·Q-005·Q-006). 기본 유지/초기화를 발명하지 않는다.
- 디자인 시스템·접근성·반응형: 관련 원본이나 지정된 목표 환경이 제공되지 않았다. 특정 컴포넌트·토큰·브레이크포인트를 확인된 제약으로 주장하지 않는다. 픽셀 배치와 일반 표현 방식은 §2.2의 재량으로 두되 위 권한·보안·행동 계약은 보존한다.
- 전송·공유 데이터 보관 기간: expires_at의 의미 외 저장·보존·삭제 정책은 주어지지 않았다. null의 보존 기간이나 공유 수명을 추정하지 않는다(Q-002).

POST 요청 필드가 있다는 사실을 request body의 JSON schema 전체가 승인됐다는 의미로 넓히지 않는다. 인증/조직 문맥 연결은 Q-003, 실제 배포·환경 확인은 Q-007이다. 200은 제공 자료의 성공 응답이며 202 접수로 바꾸지 않는다. 완료된 영속화·별도 재조회 성공·실제 실행 결과는 확인한 사실이 아니다.

- 준비 판정 이유: 네 문서 검토를 수행했으나 Q-001~Q-006이 해결되지 않아 blocked이다. 합의되지 않은 정책을 만들거나 AC 범위를 줄여 ready로 표시하지 않는다.
- 외부 의존·미확인 범위: Q-001은 계약 권위/nullable 결정, Q-002~Q-006은 제품·앱 행동 결정이다. Q-007은 알려진 계약의 배포·환경 증거 부족으로 별개다. Q-008의 후속 구간 부재는 현재 DEC-014를 자동 무효화하지 않는다.
- 후속 검증: 답변의 실제 근거를 QUESTIONS에 기록하고 SPEC 관련 규칙·AC를 갱신한 뒤 재검토한다. 구현 후 §6.1의 역할·성공·실패·null·비밀 필드 시나리오를 실제 앱에서 확인해야 한다. 문서 작성이나 구조 검사로 API/app 실행·정확성·배포가 인증되지 않는다.
