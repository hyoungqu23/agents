## 2. 질문 상세

### Q-001 — expires_at 계약의 충돌과 권위

- 원문 식별자: AC-share, api-v2.md L1·3·5, generated-client.ts L1·3.
- 질문: 필수 응답 속성 expires_at이 string 또는 null인가, string만인가? 승인된 schema·판본·적용 범위와 어느 자료가 무엇을 대체했는지 확인해야 한다.
- 근거·충돌: SRC-003은 target v2 계약 검토본에서 null 허용, SRC-004는 target v2로 전달됐으나 생성 시점·schema SHA 미상이며 null 불허다. 문서 이름·날짜·코드 형태만으로 한쪽을 최종 계약으로 선택할 수 없다.
- 현재 확인한 사실: 필수 속성 및 share_id: string, 두 요청 필드는 일치한다. nullable만 불일치하며 실서버 동작은 미관찰이다.
- 구현 영향·차단성 이유: 응답 decoder·정상 결과 타입·null 분기 및 AC-share의 완료 관찰이 달라진다. 단순 배포 대기 문제로 환원할 수 없다.
- 해결에 필요한 것: API 계약 답변자와 제품 책임자가 적용할 최종 schema 또는 명시적 결정·대체 범위를 제공해야 한다. 해당 계약 책임자는 현재 unknown이다.
- 선택지·제안: nullable 검토본 채택 또는 non-null 계약 채택을 검토할 수 있으나 어느 것도 승인된 답으로 취급하지 않는다. null을 채택하면 Q-002도 별도로 답해야 한다.
- 해결 결과: 미해결. SPEC 반영 위치: §2.2·3.2·4·5.1~5.3·6.1. 답변 후 실제 근거와 변경 판본 기록 필요.

### Q-002 — null 만료의 의미·표시

- 원문 식별자: AC-share, api-v2.md L3·5.
- 질문: null일 때 만료 자체의 의미는 무엇이고 화면에는 무엇을 표시하며 이후 어떤 사용자 행동을 허용하는가?
- 근거·충돌: SRC-003이 null의 사용자 표시·만료 정책 미정임을 명시한다. SRC-004의 string 타입은 null 의미의 답변이 아니다.
- 현재 확인한 사실: AC-share는 만료일 확인을 요구한다. null과 누락은 다르며 null을 무기한·즉시 만료·오류로 해석할 근거는 없다.
- 구현 영향·차단성 이유: null 생성 결과의 관찰·만료 안내·정상/오류 분기가 결정되지 않아 선언 범위의 AC-share를 완성할 수 없다.
- 해결에 필요한 것: 제품 책임자와 계약 책임자의 null 의미·표시·행동 결정. null이 계약에서 명시적으로 제거되면 해당 대체 근거와 null 비정상 응답 처리 근거를 함께 기록해야 한다.
- 결정권자·답변자: 제품 책임자 이선우는 DEC-014의 확정 주체로 확인됨. 이 정책의 최종 승인 체계·API 책임자는 unknown.
- 해결 결과: 미해결. SPEC 반영 위치: §3.2·4·5.2~5.3·6.1.

### Q-003 — 앱 문맥·입력·권한 연결

- 원문 식별자: FR-share·AC-share, DEC-014, api-v2.md L2, generated-client.ts L2.
- 질문: 과제 ID와 수신자 ID의 출처·선택/검증 방법, 화면 진입 문맥, 조직 관리자 여부를 식별하는 앱 권한 값·인증/조직 문맥, POST의 전송 위치·요청 형식을 무엇으로 연결하는가?
- 근거·충돌: 두 요청 속성은 필수 string으로 일치하지만 앱 entrypoint·수신자 목록·role enum·인증·wire schema는 미제공이다. 조직 관리자만 생성한다는 제품 결정 자체는 확정돼 있다.
- 현재 확인한 사실: 일반 구성원은 과제를 볼 수 있으나 생성할 수 없다. 필수 string이라는 타입은 유효 ID나 빈 문자열 정책·수신자 자격을 정의하지 않는다.
- 구현 영향·차단성 이유: 실제 입력과 권한을 얻지 못하면 생성 행동을 API에 연결할 수 없다. 임의 수신자·권한 이름·검증 규칙을 가정해서는 안 된다.
- 해결에 필요한 것: 관련 앱의 제한된 연결 계약 또는 명시적인 입력·권한·wire 요청 설명. 새 수신자 조회 API나 임의 인증 방식을 만들어 해결하지 않는다.
- 결정권자·답변자: 앱/API 연결 책임자 unknown; 권한의 제품 규칙은 DEC-014의 이선우 결정 유지.
- 해결 결과: 미해결. SPEC 반영 위치: §3.1~3.2·4·5.1~5.2·6.1.

### Q-004 — string 만료일의 형식과 표시

- 원문 식별자: AC-share, api-v2.md L3, generated-client.ts L3.
- 질문: expires_at string의 wire 형식·시간대·정확도와 사용자에게 표시할 지역/형식은 무엇인가? 해석 불가능한 string은 어떻게 다루는가?
- 근거·충돌: 두 자료는 string이라는 타입만 제시하며 ISO 형식·UTC·날짜만 표시 여부·정확한 만료 시각을 명시하지 않았다.
- 현재 확인한 사실: null 충돌과 별개로 non-null 값의 날짜 표현 계약도 없다.
- 구현 영향·차단성 이유: AC-share의 만료일을 정확하게 확인하게 하려면 값의 해석이 필요하다. 임의 시간대 변환이나 raw string을 최종 표시로 확정하면 날짜가 달라질 수 있다.
- 해결에 필요한 것: API 형식 규약과 제품의 표시 정책. 형식 오류의 사용자 회복은 Q-005와 함께 일치시켜야 한다.
- 결정권자·답변자: unknown.
- 해결 결과: 미해결. SPEC 반영 위치: §3.2·4·5.2·6.1.

### Q-005 — 생성 오류·회복과 중복 요청

- 원문 식별자: AC-share, DEC-014, api-v2.md L3~4.
- 질문: 403 not_allowed 안내와 회복, 기타 오류·네트워크 실패·필수 응답 필드 누락·파싱 실패의 계약은 무엇인가? 요청 중 동작·중복 클릭·POST 재시도·입력/기존 결과 보존은 어떻게 처리하는가?
- 근거·충돌: 검토본은 200과 403의 짧은 형상만 제공한다. 전체 오류 schema·다른 status·UI 문구·재시도/중복 방지 계약은 없다.
- 현재 확인한 사실: 403은 생성 성공이 아니며 생성 권한은 관리자에게 한정된다. expires_at null이 정상 계약일 수 있으므로 이를 자동 오류로 분류하지 않는다(Q-001·Q-002).
- 구현 영향·차단성 이유: 실패 후 사용자가 볼 결과와 다음 행동이 재구성되지 않는다. 성공으로 오인하거나 자동 재시도로 중복 생성할 수 있어 생성 흐름 완료를 막는다.
- 해결에 필요한 것: 오류 status/shape와 UI 안내·입력/결과 유지·재시도·중복 요청의 승인된 행동 계약. 해당하지 않는 실패 경로도 근거를 들어 정리해야 한다.
- 결정권자·답변자: unknown.
- 해결 결과: 미해결. SPEC 반영 위치: §3.2·4·5.3·6.1.

### Q-006 — 내보내기 경계와 비밀 필드 범위

- 원문 식별자: AC-secret, DEC-014 L3.
- 질문: 내보내기가 어떤 경로·형식·사용자 역할로 이루어지고 어떤 공유 정보를 대상으로 하는가? internal_budget·reviewer_notes 외 내부 비밀 필드와 중첩 위치·허용 출력 데이터의 목록은 무엇인가?
- 근거·충돌: SRC-001은 내보낸 공유 정보에 내부 비밀 필드 금지를 요구하고 SRC-002는 두 필드를 내보내는 UI에서도 비노출하도록 확정했다. 실제 내보내기 구현·전체 공유 데이터 schema는 없다.
- 현재 확인한 사실: 두 필드 비노출은 즉시 적용할 확정 정책이다. 두 필드만 비밀이라고 단정하거나 관리자 예외·raw 응답 전체 출력 허용을 만들 수 없다.
- 구현 영향·차단성 이유: 두 필드 제거와 비노출 검증 입력 준비는 독립적으로 가능하지만, 모든 출력 경로·비밀 필드를 모르면 AC-secret 전체를 구현·검증했다고 할 수 없다.
- 해결에 필요한 것: 실제 내보내기 계약·대상 schema와 보안 분류, 출력 경로·형식·성공/실패 동작의 설명. 클라이언트 처리인지 별도 API인지도 확인한다.
- 결정권자·답변자: 제품 책임자 이선우의 두 필드 금지 결정은 유효. 전체 내보내기/데이터 보안 분류 책임자는 unknown.
- 해결 결과: 미해결. SPEC 반영 위치: §3.1~3.2·4·5.1~5.3·6.1.

### Q-007 — 배포·생성 판본의 확인

- 원문 식별자: api-v2.md L1·5, generated-client.ts L1.
- 질문: target v2가 어느 서버·환경에 적용됐으며 생성 타입은 어떤 원본 schema 판본에서 생성됐는가?
- 근거·충돌: 배포 여부는 검토본에서도 미확인이고 생성 시점·SHA는 unknown이다. 문서나 타입을 읽은 것은 서버 호출 증거가 아니다.
- 현재 확인한 사실: target 문서와 생성 타입의 존재만 확인했다. Q-001 계약 충돌을 배포 여부 확인만으로 자동 해결하지 않는다.
- 구현 영향·차단성 이유: 실제 통합·런타임 검증에는 필요하다. 문서의 목표 계약을 정하는 결정과 구분되는 외부 환경 증거이므로 이것만으로 명세 준비를 차단하지 않는다. 현재 blocked의 원인은 별도 Q-001~Q-006이다.
- 해결에 필요한 것: 적용 환경·base URL·배포/릴리즈 근거와 생성 schema 식별. 현재 과업에서는 서버나 외부 링크에 접근하지 않았다.
- 결정권자·답변자: API/배포 책임자 unknown.
- 해결 결과: 미해결. SPEC 반영 위치: §2.1·5.1·6.2.

### Q-008 — 발췌 이후 권한 결정 확인

- 원문 식별자: DEC-014, MSG-082·MSG-083, forwarded-notes.md L1~3.
- 질문: 제공되지 않은 후속 스레드나 별도 기록에 DEC-014를 명시적으로 대체한 제품 결정이 있는가?
- 근거·충돌: DEC-014는 확정이며 대체 확인이 없다. 2026-11-09 MSG-082는 구성원 허용 제안과 무응답을 명시하고 MSG-083은 변경 시 가이드 수정이라는 조건문이다. 전달 문서 두 사본도 같은 제안일 뿐 독립 승인이나 의결이 아니다. 이후 답변 구간은 발췌에 없다.
- 현재 확인한 사실: 현재 명세는 관리자 전용 생성·일반 구성원 열람 허용·생성 금지를 적용한다. 후속 구간을 읽었다거나 결정이 바뀌지 않았음을 전체 스레드로 검증했다고 주장하지 않는다.
- 구현 영향·차단성 이유: 명시적인 대체 증거가 없는 한 확정된 DEC-014로 구현 계약이 정해져 있으므로 비차단이다. 신규 자료에 유효한 변경이 있으면 영향 범위와 §6.1을 갱신한다.
- 해결에 필요한 것: 해당 후속 원문 또는 DEC-014 대체 결정의 실제 승인 주체·범위·효력 근거. 사본 수나 더 늦은 날짜만으로는 해소되지 않는다.
- 결정권자·답변자: DEC-014 확정 주체는 제품 책임자 이선우. MSG-082 제안자는 개발자 정유리이며 제품 승인으로 보지 않는다.
- 해결 결과: 미해결. SPEC 반영 위치: §2.1~2.3·3.2·4·6.1.
