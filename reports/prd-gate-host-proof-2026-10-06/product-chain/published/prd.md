# 제품 요구사항: 기존 태그로 읽기 노트 찾기

## 문제와 근거

개인 사용자가 선택한 기존 태그로 노트를 찾으려 할 때 관련 없는 노트를 반복해서 열고, 현재는 목록을 훑는다(problem.md EV-002; SRC-001의 “repeatedly open unrelated notes”, “scan the note list”). 목표는 해당 태그가 달린 기존 노트를 정확하게 찾고 그 노트의 저장된 내용을 여는 것이다(problem.md DEC-001).

원자료와 실제 작성된 문제 문서 revision 1을 읽어 작성했다. 상위 문서의 `ready_for_review`는 문제 정의의 검토 가능성을 뜻한다. 원자료는 합성 개인 작업 사례로, 실제 고객 조사나 측정이 아니다(problem.md EV-001). 아래에서는 상위 EV-001/EV-002, DEC-001–005, AS-001의 의미와 ID를 그대로 참조한다. 별도의 새 사용자 결정은 만들지 않는다.

## 사용자, 목표와 성공 관찰

대상은 기존 읽기 노트와 정확한 기존 태그를 사용하는 개인이다. 새로운 역할이나 팀 사용은 가정하지 않는다(EV-002, DEC-002).

- GOAL-001 — 선택한 기존 태그가 달린 노트만 빠짐없이 찾는다(DEC-001). 성공은 결과 집합을 기존 태그 관계와 비교해 일치하는지 관찰한다.
- GOAL-002 — 결과에서 선택한 노트의 저장된 내용을 확인한다(DEC-001). 성공은 열린 내용이 선택한 기존 노트의 저장된 내용인지 비교한다.
- GOAL-003 — 조회 성공 후 결과가 없는 경우와 조회 실패를 눈으로 구분한다(DEC-003). 성공은 두 상황의 표시를 비교해 관찰한다.

이 관찰은 향후 수용 검증 방법이며 수행 결과가 아니다. 정량 속도 목표는 두지 않는다(DEC-002).

## 범위와 시나리오

현재 범위는 기존 태그 선택, 해당 태그의 정확한 노트 결과, 결과 노트 열기, 결과 없음과 실패의 구분이다. 다음 단계는 이 동작의 사용자 흐름 설계다(DEC-001, DEC-003, DEC-004).

1. 사용자가 기존 태그를 선택하고, 성공한 조회에서 해당 태그를 가진 기존 노트 결과를 확인한다.
2. 사용자가 결과 노트를 선택해 그 노트의 저장된 내용을 연다.
3. 조회가 성공했으나 해당 태그를 가진 노트가 없으면 결과 없음 상태를 확인한다.
4. 조회에 실패하면 결과 없음과 구분되는 실패 상태를 확인한다. 결과 노트의 내용을 읽는 데 실패한 경우에도 내용 열기 실패임을 확인한다.

태그 편집, 팀 공유, 새 인증은 제외한다. 레이아웃, 아키텍처, 저장 방식은 결정하지 않는다(DEC-002, DEC-004). 태그 의미의 재해석, 새 태그 생성, 유사 태그로 검색을 확장하는 요구는 추가하지 않는다. 기존의 정확한 태그 관계를 기준으로 한다(DEC-001). 정렬이나 화면 배치는 이 PRD의 수용 조건이 아니다.

## 요구사항과 수용 조건

### FR-001 — 기존 태그 선택과 정확한 결과

사용자는 기존 태그를 선택하여 그 태그가 달린 기존 노트의 결과를 얻을 수 있다(GOAL-001; DEC-001; AS-001).

- AC-001 — 기존 태그 T와 T가 있는/없는 노트가 주어지고 조회가 성공할 때, 사용자가 T를 선택하면 결과에는 T가 달린 모든 기존 노트가 포함되고 T가 없는 노트는 포함되지 않는다. 기존 태그 관계를 기준으로 비교한다(FR-001; GOAL-001).
- AC-002 — 사용자가 기존 태그 T에서 다른 기존 태그 U로 선택을 바꾸고 조회가 성공하면, 결과는 U의 기존 노트 집합과 일치한다. T에만 해당하는 노트가 U의 결과로 남지 않는다(FR-001; GOAL-001).

### FR-002 — 결과 노트의 저장된 내용 열기

사용자는 조회 결과에서 노트를 선택해 해당 노트의 저장된 내용을 열 수 있다(GOAL-002; DEC-001; AS-001).

- AC-003 — 성공한 조회의 결과에서 노트 N을 선택하고 내용을 읽는 데 성공하면, N의 저장된 내용이 열린다. 다른 결과 노트의 내용으로 대체되지 않는다(FR-002; GOAL-002).
- AC-004 — 결과 노트 N을 선택했지만 내용을 읽는 데 실패하면, 사용자는 N의 내용을 열지 못했다는 상태를 확인할 수 있다. 이를 성공한 내용 열기나 태그 조회 결과 없음으로 표시하지 않는다(FR-002; GOAL-002; AS-001). 이는 열기 동작의 실패 분기로 구체화한 요구이며 재시도 방식이나 오류별 정책은 정하지 않는다.

### FR-003 — 결과 없음과 조회 실패 구분

성공한 조회의 빈 결과와 실패한 조회를 눈으로 구분할 수 있게 표시한다(GOAL-003; DEC-003).

- AC-005 — 선택한 기존 태그에 해당하는 노트가 없고 조회가 성공하면, 해당 태그의 결과가 없음을 사용자가 확인할 수 있다. 조회 실패로 표시하지 않는다(FR-003; GOAL-003).
- AC-006 — 선택한 태그의 조회에 실패하면, 조회 실패를 사용자가 확인할 수 있고 AC-005의 결과 없음 표시와 눈으로 구분된다. 실패를 해당 노트가 없다는 확정 결과로 제시하지 않는다(FR-003; GOAL-003).

이 조건들은 동작 기준이며 특정 화면, 제어 요소, 문구, 데이터 읽기 기술을 지정하지 않는다.

## 제약, 의존성과 미확인 사항

AS-001(problem.md에서 유지) — 기존 노트, 태그 관계, 저장된 내용을 읽을 수 있다는 통합 가정이다. 실제 접근은 확인하지 않았다. 통합 검토에서 실제 데이터의 태그 관계와 노트 내용을 읽어 확인한다. 실패하면 구현 가능성이나 통합 범위에 영향을 주지만, 현재의 선택/열기/결과 없음/실패 흐름 설계에는 비차단이다(DEC-005). 실제 접근 제약이 새 제품 정책 선택을 요구한다는 근거가 발견되면 범위를 다시 검토한다.

현재 범위에 미해결 제품 정책 결정(OD)은 없다(SRC-001 마지막 세 문장; DEC-005). 새로운 인증·권한 정책이나 동시 데이터 변경 정책을 임의로 도입하지 않는다. 실제 데이터 접근과 변경 특성은 통합 시 확인할 사항이며, 그 확인을 수행했다고 주장하지 않는다.

## 문서 상태와 한계

`ready_for_review`: 근거, 범위, 관찰 가능한 수용 조건이 연결된 PRD 초안이다. 독립 검토 판정이나 흐름 설계 승인, 구현 승인을 뜻하지 않는다. 실제 사용자 조사, 시장 검증, 속도 측정 및 통합 테스트는 수행하지 않았다. 신규 revision 1이므로 이전 변경 이력은 없다.
